# Database Schema

## Overview

The SupportOps AI Platform stores customer support tickets, AI agent execution history, approval workflows, audit trails, authenticated users, and a support knowledge base.

The database is designed with auditability as a primary requirement. Every significant action is recorded and linked to the user or AI agent responsible.

Every table below is generated by a real Alembic migration under `alembic/versions/` (`alembic upgrade head` from the repo root) -- see `backend/database/migrations/README.md`. `knowledge_articles` and `approval_requests`'s AI-execution-context columns were, for a time, only in the SQLAlchemy models and not in any migration (added mid-sprint without regenerating one); `tests/integration/test_schema_migrations.py` now asserts the models and the live schema can never silently drift apart again.

# Entity Relationship Diagram

```
Users
   │
   │ (assigned_agent_id)
   ▼
Tickets ───────────────► Customers
   │
   ├──────────────► Agent Runs
   │
   ├──────────────► Audit Logs
   │
   └──────────────► Approval Requests   (= the supervisor queue; also
                                          carries the AI's draft response,
                                          retrieved context, selected agent,
                                          and matched policy rules)

Knowledge Articles   (standalone -- no foreign keys; read by category,
                      not linked to a specific ticket)
```

## approval_requests

Stores supervisor approval before customer responses are sent. This *is*
the supervisor queue (`GET/POST /supervisor/queue/...`) -- not a separate
placeholder table. `requested_by` is nullable: most rows today are enqueued
automatically by the workflow (policy decided `requires_human_review`), not
requested by a human user; this table was originally documented assuming
only the latter.

### Columns

| Column | Type | Constraints |
|---------|------|-------------|
| id | UUID | PK |
| ticket_id | UUID | FK tickets.id |
| requested_by | UUID | FK users.id, NULL (system/AI-enqueued when NULL) |
| approved_by | UUID | FK users.id, NULL until decided |
| status | ENUM | pending, approved, rejected |
| comments | TEXT | NULL |
| requested_at | TIMESTAMP | NOT NULL |
| decided_at | TIMESTAMPTZ | NULL -- the one timestamp column the app sets in Python (`datetime.now(UTC)`), so it's timezone-aware unlike the others below, which are all DB-side `now()` defaults |
| draft_response | TEXT | NOT NULL |
| retrieved_context | TEXT | NULL |
| selected_agent | VARCHAR(50) | NOT NULL -- e.g. `"billing_agent"` |
| matched_policy_rules | TEXT[] | NOT NULL, default `{}` -- e.g. `{refund,agent_unresolved}` |

### Relationships

Belongs to:

- Ticket
- User (requester, nullable)
- User (approver)

---

## knowledge_articles

Support knowledge-base articles CrewAI specialist agents retrieve from
(`KnowledgeBaseSearchTool`) to ground their responses, instead of relying on
the LLM's own unverifiable knowledge. Not linked to any other table by
foreign key -- `category` is a plain string matching the ticket category
values agents are scoped to (`billing`, `technical`, `account`, `general`),
not a `pg_enum`, so the database layer doesn't need to import the
graph/workflow layer's vocabulary.

### Columns

| Column | Type | Constraints |
|---------|------|-------------|
| id | UUID | PK |
| category | VARCHAR(50) | NOT NULL, indexed |
| title | VARCHAR(255) | NOT NULL |
| content | TEXT | NOT NULL |
| created_at | TIMESTAMP | NOT NULL |
| updated_at | TIMESTAMP | NOT NULL |

### Relationships

None -- a standalone reference table, read (and ranked by keyword overlap)
via `KnowledgeArticleRepository`, Redis-cached at the tool layer.

### Relationships

- User (optional)

# Cascade Rules

Deleting a customer is prohibited while tickets exist.

Deleting a ticket should never delete audit history.

Deleting users is disabled.
Users become:

```
is_active = false
```

to preserve historical references.

# Status Flow

```
NEW
 ↓
TRIAGED
 ↓
ASSIGNED
 ↓
DRAFTED
 ↓
APPROVAL_REQUIRED
 ↓
APPROVED
 ↓
SENT
 ↓
CLOSED
```

**Not yet automated.** `TicketRepository.create()` (`POST /tickets`'s real
path) always creates a ticket as `NEW` and nothing updates `tickets.status`
after that -- the LangGraph workflow's outcome (classification, draft
response, policy decision) is fully reflected in `approval_requests`
(status `pending`/`approved`/`rejected`) and `WorkflowStatus` (in-memory
only), but never written back onto the `Ticket` row itself yet. The demo
tickets `backend.scripts.seed` creates are hardcoded at various statuses for
demonstration/UI purposes, not the result of any code driving a real ticket
through this flow. See `backend/graph/README.md`'s TODO.

# User Roles

Target permission model. What's actually enforced today via
`backend.auth.dependencies.require_role` is narrower -- see the note after
each role below.

## Agent

- View assigned tickets
- Generate AI drafts
- Update ticket status

Implemented today: `POST /tickets` (any authenticated active user, not
role-restricted -- so this is really a floor every role gets, not an
Agent-specific gate). "View assigned tickets" and "update ticket status"
have no endpoint yet (no ticket-listing/status-update API exists).

---

## Supervisor

Everything an Agent can do plus:

- Approve responses
- Reject responses
- Reassign tickets
- View all tickets

Implemented today: the full supervisor queue
(`GET/POST /supervisor/queue/...` -- view, approve, edit, reject), gated by
`require_role(UserRole.SUPERVISOR, UserRole.ADMIN)`. "Reassign tickets" has
no endpoint yet.

---

## Admin

Everything plus:

- Manage users
- View audit logs
- Configure platform settings
- System administration

Implemented today: nothing Admin-specific yet -- `require_role(...,
UserRole.ADMIN)` everywhere it's used also accepts Supervisor, so Admin
currently has the same effective access as Supervisor. None of "manage
users," "view audit logs" (as an API), or "configure platform settings" has
an endpoint yet.

# Design Principles

- UUID primary keys for all tables.
- JSONB used for AI inputs, outputs, and metadata.
- Audit logs are immutable.
- Users are soft-deleted using `is_active`.
- Every AI execution is traceable.
- Every approval is recorded.
- Every ticket action is auditable.
